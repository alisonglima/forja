A forja dubla vídeos para o português e monta vídeos por cenas com narração no Google AI Studio por padrão — ou com modelos locais, se você preferir. Você conversa com o seu agente de IA; ele roda os comandos, confere o resultado e pede a sua decisão quando é hora de escolher.

01

O que a forja faz

Duas tarefas, o mesmo jeito de trabalhar. Você entrega o material, as contas e as decisões; o agente cuida do caminho técnico.

workflow dub

Dublar um vídeo

Pega um vídeo em inglês, transcreve, adapta o texto com você, usa as vozes que você gerou, mixa por cima do áudio original com ducking e queima a legenda no vídeo.

  • Entra: input/source.mp4 + voices/<id>.wav
  • Sai: out/video.mp4, legendas.srt, qa.json
workflow storyboard

Criar por cenas

Monta um vídeo do zero a partir de um storyboard.yaml: clipes (gerados no Google Flow ou locais), narração que você gerou, cards, trilha e legendas, cena por cena.

  • Entra: storyboard.yaml + assets/ + voices/<cena>.wav
  • Sai: out/video.mp4, legendas.srt, qa.json

Quem decide o quê

seu papel
  • Escolher a voz e aprovar o elenco.
  • Fechar o texto final da dublagem.
  • Confirmar direitos, consentimento e aviso de IA.
  • Autorizar qualquer gasto (API é opcional).
  • Publicar — e decidir onde.
papel do agente
  • Rodar doctor, status, run e qa.
  • Transcrever, extrair quadros e propor o texto.
  • Escrever cues.json e storyboard.yaml.
  • Validar e normalizar as vozes que você forneceu.
  • Ler o erro, corrigir e só então te chamar.

O ciclo de trabalho

  1. Veja o estado.

    ./kit.sh run --project /projects/meu-video --json status mostra cada passo e o campo next_actions.

  2. Faça o próximo passo.

    Muitas vezes o passo é do agente: escrever as cues, montar o storyboard, validar as vozes. Ele pede a sua decisão quando precisa.

  3. Rode o pipeline.

    ./kit.sh run --project /projects/meu-video --json run roda só o que mudou: o cache é por hash das entradas.

  4. Confira o portão de qualidade.

    ./kit.sh run --project /projects/meu-video --json qa --strict. Saída 1 quer dizer reprovado: leia os issues antes de entregar.

a regra de ouro

O agente não escolhe voz, não publica e não gasta além do combinado sem você. As contas são suas; o kit só orquestra o trabalho determinístico.

Antes de começar

Máquina

Windows 10/11 com WSL2 ou Linux, ambos x86_64. Docker com Compose v2. 8 GB de RAM (16 GB é melhor) e 25 GB livres.

Imagem

Cerca de 1,8 GB para o pipeline. O Chromium opcional do modo avançado acrescenta uns 2,6 GB.

Internet

No primeiro build e para baixar o modelo de transcrição uma vez. Depois, só o provedor de voz que você escolher precisa de rede — e o vídeo/áudio original não é enviado pelo kit.

Começar em 5 passos

  1. Prepare o kit.

    ./kit.sh setup cria o .env, uma senha aleatória do navegador e as pastas projects/ e models/.

  2. Escolha as vozes.

    O padrão é google_ai_studio: gere as vozes na interface web do AI Studio e salve em projects/<nome>/voices/<id>.wav. piper é a alternativa offline opcional; files é alias para qualquer WAV e gemini é API opcional.

  3. Construa a imagem.

    ./kit.sh build. É a parte demorada; só acontece na primeira vez (ou quando o kit muda).

  4. Ensine o seu agente.

    Copie o prompt 02 desta página e cole no seu agente. Ele instala a skill e passa a saber operar a forja.

  5. Peça o vídeo.

    Use o prompt 03 para dublar um vídeo existente ou o prompt 08 para criar um vídeo por cenas.

mapa do kit

kit.sh (atalhos) · compose.yaml (container) · .env (senha do navegador e opções; fora do git) · voices/ (suas vozes) · prompts/ (15 mensagens) · projects/ (seus vídeos) · docs/index.html (esta página) · skills/forja/ (a skill do agente).

02

Brief e aprovação humana

O humano define o que importa; o agente faz o resto. O brief.yaml é a fonte dos requisitos e o approvals.json é o registro de quem aprovou.

O brief

objective, audience, tone, duration_s, must_include, must_avoid e consent. O agente lê e usa como restrição; o check/validate avisa quando falta algo.

A aprovação

Quatro chaves: script, voice, overlays e publish. O render exige as três primeiras quando project.require_approvals está ligado.

O gate

Sem as aprovações, o passo render falha com GATE_FAILED. É de propósito: o agente não publica nem renderiza por conta própria.

  1. Crie o projeto.

    ./kit.sh new <nome> <vídeo> ou forja init <dir> cria brief.yaml, approvals.json e liga require_approvals. Em demo/teste, forja init --no-require-approvals desliga o gate.

  2. Preencha o brief com o humano.

    Objetivo, público, tom, duração, o que não pode faltar e o que não pode aparecer. O agente pergunta; não inventa requisito.

  3. Revise e aprove.

    Depois de ler o roteiro, o elenco e o plano de overlays, o humano roda forja approve --script --voice --overlays --by "Nome". Publicar é uma aprovação separada (--publish).

  4. Rode o pipeline.

    O render só começa com as aprovações. Se o roteiro mudar, aprove de novo: o gate não é um carimbo eterno.

por que isso existe

O agente é ótimo no trabalho determinístico e ruim em julgamento de marca, voz e consentimento. O brief e a aprovação deixam a decisão com uma pessoa — e dão ao agente um contrato claro para seguir.

03

Modo padrão: Google AI Studio

O caminho padrão é o Google AI Studio, com a sua conta, sem chave de API. O Piper local é o plano B offline; os dois alimentam o mesmo pipeline.

  1. Crie a configuração.

    ./kit.sh setup copia o .env.example, gera a senha do navegador, ajusta o seu UID/GID e cria projects/ e models/.

  2. Escolha o caminho de voz.

    O padrão é voices.provider: google_ai_studio: você gera as vozes na interface web do AI Studio e salva em projects/<nome>/voices/<id>.wav. Para autonomia offline, troque para piper (voz pt-BR na imagem). files é alias para qualquer WAV; gemini é API opcional.

  3. Gere as vozes.

    No Google AI Studio (padrão), abra a interface com a sua conta, gere a fala de cada cue e salve um WAV PCM em projects/<nome>/voices/<id>.wav. No piper, rode o passo voices e o kit sintetiza localmente. O kit valida, normaliza e mixa.

  4. Confira o ambiente.

    ./kit.sh doctor mostra Docker, Compose, arquitetura, espaço em disco e o provedor de voz. Se você optar por API, a chave aparece só como definida ou ausente — nunca o valor.

  5. Construa a imagem.

    ./kit.sh build. O Docker baixa a base, instala ffmpeg, Python, Whisper, Piper + voz pt-BR e o Chrome Headless do Remotion. Vai demorar alguns minutos na primeira vez.

  6. Entregue o volante ao agente.

    Copie o prompt 02 para instalar a skill. Depois use o prompt 03 (dublar) ou os prompts 08 + 14 (cenas + Google Flow) e responda às perguntas dele.

AI Studio é o padrão; Piper é alternativa

O AI Studio usa a sua conta Google, os termos do Google e pode ter limites/cota; pare se pedir verificação. O piper não é o setup atual: é um TTS local opcional, com uma voz, qualidade abaixo do AI Studio, piper-tts GPL-3.0 e modelo MIT/CC0. Use-o só para autonomia offline ou teste; para elenco e qualidade, prefira o AI Studio.

nenhuma chave obrigatória

Nos modos google_ai_studio/files/piper, o kit não fala com nenhum serviço de voz: ele lê os WAVs que você gerou ou sintetiza localmente. Se você escolher um provedor por API, a chave é sua, fica no .env e o gasto é decidido por você.

04

Cenas: Google Flow por padrão

O caminho padrão para os clipes é o Google Flow, aberto no navegador já logado com a sua conta e os seus créditos. O agente opera a interface e baixa os takes; o Forja não chama o Flow por API.

Como funciona

Você loga no Flow no navegador (desktop ou container). O agente escreve os prompts de cena, gera 2–4 takes, baixa o melhor MP4 e salva em assets/flow/; depois atualiza o storyboard.yaml.

O que o Forja faz

Valida o storyboard, resolve a timeline, mixa a narração/trilha e renderiza no Remotion. Ele não gera o clipe nem chama o Flow: a integração é o navegador, não uma API.

Custo e limites

Cada geração consome créditos e pode exigir plano pago. Confirme o custo com o humano antes de gerar em lote; não contorne fila, captcha, limite ou política de conteúdo.

  1. Feche o plano de cenas.

    Leia o brief.yaml e o storyboard.yaml: duração, enquadramento, câmera, luz, estilo e o que não pode aparecer. Se o storyboard ainda não existir, proponha as cenas e espere a aprovação.

  2. Abra o Flow na conta certa.

    Use o navegador do prompt 10 (desktop) ou 11 (container), já logado. Confirme a conta e o saldo de créditos na tela. Se aparecer verificação, pare e chame o humano.

  3. Gere e baixe os takes.

    Para cada cena, escreva um prompt específico e gere 2–4 takes. No Flow, peça somente SFX e som ambiente — sem fala, sem narração, sem diálogo, sem música e sem legenda na imagem; a narração vem do AI Studio e a trilha é a camada music licenciada. Baixe o melhor MP4 para assets/flow/<cena>-v1.mp4 e registre prompt, take, data e créditos gastos.

  4. Atualize o storyboard.

    Adicione as camadas clip com file, in_s e fit. Rode forja run --only validate e corrija os issues. O áudio embutido do clipe entra no bed por padrão; use audio: {mode: mute} se o Flow gerar fala/música por engano. Exceção: vídeo que já traz áudio que não pode ser removido (ex.: dublagem de um vídeo gravado) é trabalhado sobre o áudio original, que fica ao fundo com ducking sob a narração.

  5. Aprove e renderize.

    Mostre os takes e os créditos ao humano; com roteiro/voz/overlays aprovados, rode forja approve e o pipeline normal.

ressalvas que não podem faltar

Flow é interface, não API: a automação depende da UI, da conta e dos créditos e pode quebrar quando o Google mudar a tela. Não determinístico: o mesmo prompt pode gerar resultados diferentes; guarde prompt/take/versão. Conteúdo e direitos: siga os termos do Google Flow/Labs, políticas de conteúdo e regras de uso comercial; vídeos podem ter marca d'água/SynthID. Pessoas e marcas: não gere pessoas reais, marcas ou cenas sensíveis sem autorização. Privacidade: não suba material confidencial sem autorização. Áudio: o áudio embutido do clipe entra no bed por padrão (use audio: {mode: mute} para remover); sfx entra e exige license.kind. A narração vem do AI Studio e a trilha é uma camada licenciada.

05

Modo avançado: navegador no container

Para quem quer a interface do provedor numa aba do navegador normal, sem ocupar a área de trabalho — e para quem optar por um provedor de voz por API.

  1. Suba o navegador.

    ./kit.sh browser-up inicia o Chromium e um proxy que deixa o CDP acessível apenas no seu loopback. A senha já foi gerada no .env; pegue-a no arquivo, não a imprima.

  2. Entre na tela.

    Abra https://localhost:3001, aceite o certificado autoassinado e use o usuário e a senha do .env.

  3. Faça o login com a sua conta.

    O login acontece dentro desse ambiente. O perfil fica num volume Docker e sobrevive a reinícios. A sessão não é copiada de outra máquina — e não deve ser.

  4. Gere as vozes e salve os WAVs.

    Use a interface para gerar a fala de cada cue e salve em projects/<nome>/voices/<id>.wav. O agente pode conduzir por CDP em 127.0.0.1:9222 (Playwright MCP ou computer use).

  5. Opcional: provedor por API.

    Se você preferir automatizar a síntese, configure voices.provider: gemini, voices.model e a sua chave no .env. O caminho padrão continua sendo google_ai_studio.

  6. Termine com cuidado.

    ./kit.sh browser-down desliga e mantém o login. ./kit.sh browser-reset apaga o perfil — depois revogue a sessão na conta do provedor.

cuidado real

O terminal web da imagem do Chromium tem sudo sem senha. Quem alcança a tela vira root dentro do container. Por isso as portas 3001 e 9222 ficam presas em 127.0.0.1 e nunca devem ser publicadas na rede. Em máquina compartilhada, não deixe a tela aberta.

06

Sem Docker: execução direta

Alternativa para máquina simples, sem VPS ou sem Docker. A CLI roda direto no Windows, macOS ou Linux, com Python, Node, ffmpeg e Chrome do sistema. É uma opção, não o caminho padrão do kit.

Quando faz sentido

Você já tem Python/Node/ffmpeg, quer testar rápido ou não quer uma imagem de ~2 GB. Serve para edição local e para quem não tem servidor.

O que você perde

Sem versões presas e sem isolamento de container. O `kit.sh` não é usado; você chama python -m forja. O navegador é o seu normal, não o Chromium do kit.

O que precisa

Python 3.9+, ffmpeg/ffprobe com libx264, Node 20+ e Chrome Headless via Remotion. 8 GB de RAM e ~4 GB livres; o Whisper baixa o modelo na primeira vez.

Instalação rápida

O script cria .venv, instala .[test], roda npm install no template do Remotion, baixa o Chrome Headless Shell e chama o doctor. Se faltar ffmpeg/Node, ele para e diz o que instalar.

07

Como as peças se encaixam

Você fala com o agente. Ele roda o kit.sh. O kit.sh chama o Docker. Dentro do container, a CLI orquestra ffmpeg, Whisper, Remotion e o provedor de voz que você escolher.

O que atravessa a fronteira

Fica na sua máquinaSai para a internet
Vídeo, áudio, quadros, transcrição, cues, storyboard, saídas.O texto da narração enviado ao provedor de voz que você escolher (voltam os arquivos de voz).
As suas contas e, se houver API, a chave no .env.Downloads do primeiro build e o modelo do Whisper, baixados uma vez.
O cache por hash e o work/events.ndjson.Nada de vídeo ou áudio original é enviado pelo kit.

Por que um container

Repetível

O mesmo comando funciona no Windows (WSL2) e no Linux. As versões de ffmpeg, Python, Node e Chrome ficam presas na imagem.

Isolado

Roda com o seu UID/GID (nunca root), com cap_drop: ALL, no-new-privileges e limites de CPU e memória.

Portátil

Só duas pastas são montadas: projects/ e models/ (cache de modelos). O resto do seu disco não é visível para o pipeline.

Dentro do container

  • ffmpeg — corta o trecho, extrai o áudio, aplica o ducking, normaliza o loudness e muxa o resultado.
  • Whisper (faster-whisper) — transcreve em CPU, com timestamps por palavra, sem mandar o áudio para fora.
  • Remotion + Chrome Headless Shell — desenha as legendas e o vídeo por cenas quadro a quadro.
  • CLI forja — decide o que rodar, guarda o cache, escreve os eventos e aplica o portão de QA.
  • Provedor de voz — o Piper roda dentro do container, sem rede; os modos files/API usam a sua conta/interface ou, se optar, uma chave.

Áudio, sfx e âncoras por palavra

O bed do storyboard soma narração, música, áudio embutido do clipe e sfx; a narração faz ducking do bed. Cada clipe pode ajustar o próprio áudio:

- type: clip
  file: assets/flow/cena-01.mp4
  audio: {mode: keep, gain_db: -6}   # mute remove; duck deixa o ducking global
- type: sfx
  file: assets/sfx/whoosh.wav
  license: {kind: "cc0"}             # obrigatório
  gain_db: -12
  duration: 0.8
  enter: {anchor: word, word: "começa"}

enter/exit com {anchor: word, word: "..."} usam o tempo real da palavra. O passo timeline transcreve só as cenas que têm âncora por palavra com faster-whisper e guarda em work/words/<cena>.json. Se a transcrição falhar, se a palavra não for encontrada na narração ou se faltar o WAV da narração (work/voices/<cena>.wav), o passo timeline retorna MISSING_PREREQ; não há alinhamento fingido.

MCP (stdio)

Para agentes que preferem tools a shell, a CLI tem um servidor MCP por stdio, JSON-RPC 2.0, uma mensagem por linha, sem SDK extra:

forja mcp serve

As tools chamam a mesma CLI e devolvem o JSON no content: forja_describe, forja_providers, forja_status, forja_doctor, forja_init, forja_run, forja_qa, forja_approve. O servidor não abre porta, não imprime segredos e não substitui as aprovações humanas.

por que isso importa

O agente pode errar um comando sem estragar a sua máquina: o pior caso é um arquivo em projects/. E o QA é um portão de verdade — qa --strict sai com código 1 quando o vídeo não passa.

Overlays profissionais

Sete presets prontos, tema de marca e ajuste por camada. O overlay entra na timeline do storyboard.yaml e é desenhado pelo Remotion, junto com a legenda.

- type: overlay
  preset: lower_third
  text: "Ana Silva"
  subtext: "Diretora de produto"
  position: bottom-left
  enter: {anchor: scene_start, offset_s: 0.6}
  hold_s: 3.5
  style: {accent: "#C24B2A", ink: "#1A1714", paper: "#F6F1E8"}

Tema de marca

brand no config.yaml: primary, ink, paper, accent, font, logo e safe_margin. Cada overlay pode sobrescrever style (cor, fonte, tamanho, raio, opacidade, largura e alinhamento).

Legenda sem colisão

Quando um overlay fica na parte de baixo, o passo timeline marca a legenda como raised e o Remotion sobe o bloco. O lower-third e a legenda não se sobrepõem.

Validação

Preset, texto, posição, hold_s, estilo e asset são validados no validate. Asset fora da raiz ou ausente vira ASSET_*; preset inválido vira OVERLAY_*.

regra de composição

Um overlay principal por cena. Não empilhe título + lower-third + CTA no mesmo instante; o vídeo fica limpo e o olho sabe onde olhar. O agente mostra o plano de overlays antes de renderizar.

00

Instalar o Docker

Quando usar: Quando a maquina ainda nao tem Docker ou o Docker nao esta funcionando.

Dublagem: adaptar o roteiro

Quando usar: Transforma a transcricao em cues em portugues que cabem no tempo.

Você é um **adaptador de dublagem** inglês→português do Brasil. Entradas: `work/transcript.json`, a tabela de falantes e `lower_thirds.json` do projeto `projects/<NOME>`, mais o que eu corrigi. Saída: `projects/<NOME>/cues.json` e um glossário de pronúncia.

Ciclo: `init` → `transcribe` → `frames` → `cues.json` → `check` → `voices` → `run` → `qa --strict`. Aqui estamos no `cues.json` e no `check`.

Formato de cada cue (lista JSON):
`{"id": "A", "speaker": "voluntario", "role": "speech", "t0": 12.3, "t1": 16.8, "lead": 0.3, "text": "…pt-BR…", "source_text": "…inglês original…"}`
- `role: "speech"` = narração por cima de uma pessoa que fala (a voz original fica ao fundo, mais baixa). `role: "narrator"` = narração própria do vídeo.
- `t0`/`t1` = início e fim da fala **original** em segundos (use os tempos das palavras do transcript). `lead` = atraso da narração depois do início (0,3 s por padrão; até 0,9 s em frases longas que começam rápido).
- `id` únicos (A, B, C…).

Regras de adaptação (rígidas):
1. Dublagem de documentário: **intenção e registro** acima de tradução literal. Português falado, natural. Preserve nomes próprios, números, siglas e o que a pessoa realmente disse; **não acrescente informação, opinião, promessa ou número**; pode omitir redundância e vocativos.
2. **Caber no tempo.** A voz fica entre **0,9× e 1,2×** da duração original; acima disso soa acelerada. Encurte o texto — **não conte com acelerar**. Referência: ≈ 2,8 palavras por segundo.
3. Legenda (a mesma frase): máximo **42 caracteres por linha, 2 linhas**, e ≤ **20 caracteres por segundo** na janela `t1 − t0`.
4. Números e valores escritos como se falam ("mil e trezentos dólares"). Quebre frases longas em cues separados quando a pessoa respira.
5. Coloque em `voices.glossary` no `config.yaml` as palavras que o locutor pode pronunciar mal (marcas, nomes em inglês, siglas), com a grafia fonética em português, ex.: `"<MARCA>": "<pronúncia>"`.

Depois de escrever:
- Rode `./kit.sh run --project /projects/<NOME> --json check`. Ele lista problemas com código (`MISSING_FIELD`, `DUP_ID`, `T_ORDER`, `LINES`, `CPS`, `BUDGET`, `OVERLAP`). **Corrija todos os `error`** e repita até passar; avalie cada `warn`.
- Me mostre uma tabela `id | falante | original | português | palavras/s` para revisão minha antes de gerar áudio. **Pergunte a mim o texto final dos cues** e diga o que ficou incerto.

Use `forja status` e o campo `next_actions` para confirmar o próximo passo. Metas de qualidade: 42 caracteres × 2 linhas, ≤ 20 CPS, voz entre 0,9× e 1,2×, loudness final −16 LUFS. Reporte os cues, os problemas corrigidos e o glossário. Diga o que **não verificou**: se o texto cabe de fato na voz (só o `check` estima) e se a tradução preserva todas as nuances.

No modo avançado, 3001 (a tela, com senha) e 9222 (o CDP, sem autenticação própria) escutam só em 127.0.0.1. Quem alcança o CDP, controla.

O login fica no ambiente final

Faça o login na conta do provedor dentro do navegador do kit. Não copie perfil ou cookies entre máquinas: a sessão é do dispositivo e não deve viajar.

As contas são suas

Use a sua conta e a sua ferramenta de voz. Não compartilhe login, não empreste chave e não deixe a tela do Chromium aberta em máquina compartilhada.

Flow é conta e créditos

A geração de cenas no Google Flow usa a sua conta e consome créditos. O agente opera a UI; não há API do Forja para o Flow. Confirme custo/limite antes de gerar em lote e não contorne captcha ou política.

Aprovação é humana

brief.yaml registra objetivo/público/tom; forja approve registra roteiro/voz/overlays. Com require_approvals, o render falha com GATE_FAILED sem essas chaves.

Consentimento é de quem publica

Voz sintetizada de pessoa real pede autorização e aviso. O prompt 12 monta a pasta de conformidade com você; a decisão final é sempre humana.

se algo vazar

Se você usa um provedor por API, gere outra chave e atualize o .env. Se o problema for o navegador, rode ./kit.sh browser-reset e revogue a sessão na conta do provedor. O work/events.ndjson foi feito para não guardar segredo: chaves nos nomes dos campos são descartadas.

O Chromium pode rodar minimizado?

Pergunta curta, resposta honesta: não é confiável. Janela minimizada ou totalmente coberta conta como oculta para o navegador.

por que não

O Chrome reduz timers, animações e trabalho de renderização quando a janela não está visível. O CDP até responde, mas a página pode travar, atrasar ou desenhar errado. Para automação de verdade, a janela precisa estar visível — mesmo que em outra área de trabalho.

modo padrão

Outra área de trabalho

Use um perfil de navegador dedicado e deixe a janela visível num desktop virtual: Windows Win+Ctrl+D, macOS Mission Control, Linux outro workspace. Não minimize.

modo avançado

Container + aba

O Chromium roda no Docker e aparece numa aba do seu navegador normal. A página continua viva no container, sem depender da sua área de trabalho.

sempre

As contas são suas

A interface com a sua conta é o caminho padrão. A API é opcional e só entra se você configurar. Em qualquer modo, não compartilhe a conta nem copie a sessão para outra máquina.

Quando algo dá errado

Não adivinhe a causa. Leia o erro literal, reproduza com o menor comando possível e só então conclua. O prompt 13 conduz o agente por essa ordem.

  1. Comece pelo ambiente.

    ./kit.sh doctor. Docker, Compose, arquitetura, provedor de voz e disco. O doctor da CLI (forja --json doctor) vê ffmpeg, ffprobe, node e as bibliotecas.

  2. Veja os containers.

    docker compose ps -a e docker compose logs --tail 80 forja (ou browser).

  3. Pergunte à CLI o que falta.

    ./kit.sh run --project /projects/meu-video --json status devolve o estado de cada passo e next_actions.

  4. Leia o rastro.

    projects/meu-video/work/events.ndjson tem um evento por passo, com início, fim e o erro. O último failed é o que importa.

  5. Traduza o código.

    No --json, olhe error.code, error.hint e retryable. A dica já diz o que corrigir; retryable: true pode ser repetido.
